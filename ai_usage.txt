Task 1 (member function declaration and call):
- parser.py: тіло struct тепер розрізняє дві фази (поля, потім fn) з двома
  дзеркальними помилками з методички — fn до першого поля і поле після fn, кожна
  в точному рядку. parse_fn розбитий на parse_fn_rest() (усе після ключового слова
  "fn"), яким користуються і parse_fn, і новий parse_member_fn — без дублювання
  логіки параметрів. parse_factor для ідентифікатора тепер читає "." ланцюжок по
  одному імені, і після кожного перевіряє наступний токен — "(" завершує ланцюжок
  як member_call (parse_member_call, об'єкт — FieldNode з накопиченими полями або
  VarNode), інакше ім'я йде в список полів. looks_like_a_call() — заглядання вперед
  без споживання токенів за шаблоном "ident {'.' ident} '('" — однаково ловить
  "f(1)" і "p.shift(2)" одним повідомленням "a call cannot stand alone as a
  statement".
- checker.py: declare_struct додатково оголошує сигнатури функцій-членів після
  полів і перевіряє колізії імен (поле/функція-член, дві функції-члена).
  resolve_chain (спільна для visit_field/visit_assign/visit_var) отримала третю
  гілку: якщо базове ім'я не знайдено серед локальних/параметрів, але є поле з
  таким іменем у поточній структурі (self.current_struct), ланцюжок стартує так,
  наче перед ним стояло неявне "self." — базовий "decl" для цього випадку це сам
  self.current_fn (MemberFnNode), той самий ключ, яким потім користується
  CodeGen.ptrs у compiler.py для вказівника на отримувача. visit_member_call шукає
  функцію в struct.member_fns за типом об'єкта.
- gen.py/compiler.py: член-функція отримує в IR один додатковий перший параметр —
  вказівник на об'єкт; CodeGen.ptrs[MemberFnNode] = цей вказівник напряму (без
  alloca, бо це вже вказівник) — той самий gep_chain, яким користується решта коду
  для звичайних alloca-вказівників, працює без змін.

Task 2 (names, mutation, code generation):
- Виправив іменування в IR: за методичкою функція-член має називатися рівно
  "Point_shift" (не "fn_Point_shift", як я зробив у Task 1), перший параметр
  названо "this".
- Видимість імен: параметр/локальна змінна ховає однойменне поле — це вже
  працювало саме завдяки порядку перевірки в resolve_chain (спочатку
  lookup_optional серед локальних, лише потім неявне self-поле), жодних змін не
  знадобилось. Виклик f(...) без крапки всередині функції-члена тепер спершу
  шукає серед функцій-членів тієї ж структури (self.current_struct.member_fns), і
  лише потім серед глобальних — функція-член ховає глобальну з тим самим іменем;
  у gen.py такий виклик (node.on_self) передає self.self_ptr (вказівник поточної
  функції на власний отримувач) першим аргументом.
- Правило mutating: кожна функція-член при перевірці тіла накопичує
  direct_mutates (чи є пряме присвоєння полю, досяжному від self — перевіряється
  в visit_assign через decl is self.current_fn) і calls (список функцій-членів,
  викликаних на self або на полі self — з бар-виклику чи з member_call, де
  obj.decl is self.current_fn). Після перевірки УСІХ тіл програми (а не одного
  struct — поле іншого типу struct може викликати mutating-метод того типу)
  compute_mutating рахує нерухому точку: починає з direct_mutates, тоді повторює
  позначення функцій, що викликають уже позначену, поки нічого нового не
  додається — так підтримуються цикли викликів між функціями-членами.
  resolve_chain тепер завжди рахує chain_mut (mut усього ланцюжка, не лише коли
  require_mut=True) і зберігає його на VarNode/FieldNode як .mut — member_call
  запам'ятовує себе в self.pending_member_calls, а фактична перевірка "чи можна
  викликати mutating-метод через цей ланцюжок" відкладена до
  validate_pending_member_calls, що викликається раз наприкінці check(), коли
  is_mutating вже остаточний для кожної функції-члена — так приклад з методички
  (q.shift(1) на немутабельному q, c.center.shift(1) через немутабельне поле
  center) перевіряється буквально.
- Побічно знайдений і виправлений баг: функція-член, що повертає чи приймає тип
  своєї ж структури (fn moved := (i32 dx) -> Point у struct Point), падала з
  "unknown result type 'Point'", бо структура реєструвалась у self.structs лише
  після перевірки сигнатур усіх своїх функцій-членів. Поле досі не може мати тип
  своєї ж структури (нескінченний розмір), але метод — може (бачить лише через
  вказівник або повертає вже готове значення) — реєстрацію структури перенесено
  до циклу полів, перед циклом функцій-членів.

Task 3 (read()/print()):
- lexer.py: новий стан STRING (байт за байтом до закриваючої '"' або кінця рядка/
  файлу — у другому випадку помилка саме в позиції відкриваючої '"', без escape-
  послідовностей, decode через latin1, щоб жоден байт 0-255 не впав з помилкою).
  "print" доданий до KEYWORDS (як "if"/"exit" — тому ім'я "print" неможливо
  використати як змінну/поле/параметр/функцію на рівні лексера й парсера
  автоматично, без окремих перевірок у checker.py). "read" НЕ ключове слово — за
  граматикою методички read() розбирається звичайним правилом call (lowercase
  ident), тому зарезервовано лише семантично: check_not_reserved викликається в
  усіх місцях, де з'являється нове ім'я (поле, функція-член, глобальна функція,
  параметр, локальна змінна).
- ast_nodes.py/parser.py: нові StringNode і PrintNode; parse_print (окрема гілка
  в parse_statement за ключовим словом "print", працює скрізь, де працює
  parse_statement — у блоках if/while/fn/функцій-членів теж, без додаткового
  підключення). Явні помилки для print() без аргументу, print(a, b) і рядкового
  літерала поза print (в останньому випадку — прямо в parse_factor, бо "string"
  просто не альтернатива factor).
- checker.py: visit_call спершу перевіряє node.name == "read" (вбудований білтин,
  перевіряє 0 аргументів, тип i32) — раніше за пошук серед функцій-членів/
  глобальних функцій, тому не може зіткнутися з жодним іменем (read зарезервоване
  всюди). visit_print нічого не обмежує для expr-аргументу (друкується будь-який
  тип) і нічого не перевіряє для рядкового літерала (в нього немає типу).
- gen.py/compiler.py: printf/scanf більше не прив'язані лише до верхнього рівня —
  print може з'явитися в будь-якій функції чи функції-члена, тож усі екземпляри
  CodeGen тепер ділять один runtime-об'єкт rt (module, i8, printf, scanf, формати,
  спільний itertools.count() для унікальних імен рядкових глобалів). Жоден глобал
  більше не біткаститься наперед одним білдером — CodeGen.as_ptr біткастить
  "по місцю", білдером ПОТОЧНОЇ функції, бо біткаст — інструкція, і інструкція з
  одного тіла функції не може бути значенням в іншому. gen_print_value рекурсивний
  і не знає нічого спеціального про жодну конкретну структуру — просто йде по
  struct.field_order з extract_value, тому новий struct друкується без жодного
  нового коду в компіляторі (буквально за методичкою). read() — scanf в alloca
  в entry block, потім load (той самий патерн, що й усі інші alloca).

Додаткове завдання (виклик у середині ланцюжка):
- Новий вузол ChainFieldNode (base.field, де base — сам вираз: виклик, member
  call або інший ChainFieldNode, а не named-змінна — той випадок уже покриває
  FieldNode). parse_chain_tail — після побудови call/member_call перевіряє, чи йде
  "." далі: "." ident без "(" — ChainFieldNode (читання поля тимчасового
  значення), "." ident "(" — ще один MemberCallNode, цього разу з obj, що не є
  Var/FieldNode (а сам call/member_call/ChainFieldNode). Парсер приймає "."
  після виклику завжди, без жодної перевірки типу — чи справді результат
  структура, вирішує checker.py (visit_chain_field: якщо тип не struct —
  помилка "cannot read '.x' of a value of type i32" рівно в позиції крапки,
  як просить методичка на прикладі p.d2().x).
- checker.py: node.obj.decl/.mut можуть просто не існувати, коли obj — тимчасове
  значення (getattr(..., None)/getattr(..., True) замість прямого доступу) —
  тимчасове значення завжди "досить мутабельне", щоб викликати на ньому
  будь-який метод, включно з mutating (буквально за методичкою: "the result is
  a temporary copy ... any member function can be called on it, also a mutating
  one"), і ніколи не додає ребро в граф mutating (виклик на тимчасовому не
  впливає на жоден реальний об'єкт).
- gen.py: visit_member_call розрізняє "obj має .decl" (gep у вже наявну
  alloca/this, як у Task 1) і "obj — тимчасове" (обчислити значення через
  obj.accept(self), покласти в свіжу alloca в entry block, передати її адресу як
  this — буквально "for a member function call the result is stored into a
  temporary alloca, and its address is passed as this" з методички).
  visit_chain_field — одне extract_value за індексом, який уже знайшов checker.
- Приклад з методички (Point/Circle/moved/shift/grown/origin, p.moved(1).shift(2)
  і решта) дає рівно 46, як і обіцяно; p лишається const (3), бо shift міняє
  копію.
